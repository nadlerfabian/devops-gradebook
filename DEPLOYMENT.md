# Gradebook deployment runbook

The project owner manages the GitHub repository and the Render service. Use a
GitHub account with repository access, a Render account that can connect to
that repository, Git, Python 3.12, and Docker Desktop for local image checks.
Check the tools with `git --version`, `python --version`, and `docker version`.

## Run locally

```powershell
git clone https://github.com/nadlerfabian/devops-gradebook.git
cd devops-gradebook
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m flask --app wsgi run --port 8000
```

In a separate terminal, run `Invoke-RestMethod http://127.0.0.1:8000/health`.
The default response has status `ok` and version `0.0.0-dev`. The
[Compose instructions](README.md#local-docker-compose-stack) cover local
PostgreSQL, and the [login guide](docs/AUTHENTICATION.md) covers demo accounts.

## First Render deployment

1. Merge the Blueprint into `main` through a green pull request.
2. In the [Render dashboard](https://dashboard.render.com/), choose
   **New → Blueprint** and connect `nadlerfabian/devops-gradebook`.
3. Select `main` and use the root `render.yaml`. Review the proposed
   `devops-gradebook` web service. It uses Docker, the root Dockerfile,
   the Frankfurt region, and the Free plan.
4. Enter separate synthetic passwords for `DEMO_LECTURER_PASSWORD` and
   `DEMO_STUDENT_PASSWORD` when prompted. Render generates the signing key.
5. Deploy the Blueprint. Open the new service and wait for the first deploy
   to be live. Record the public URL and deployed commit from the dashboard.
6. Confirm service auto-deploy is Off. Disable Blueprint Auto Sync after
   provisioning so later Blueprint changes are applied deliberately. The
   GitHub Actions deployment workflow will be added after this first check.

The Free web service can spin down when idle. This deployment uses one
Gunicorn worker and in-memory storage for synthetic data, so records reset
when the app restarts, spins down, or redeploys. Compose with PostgreSQL
remains the persistence demonstration. A Render Free Postgres instance would
expire after 30 days. See [Render free service limits](https://render.com/docs/free).

## Configuration

| Variable | Default or source | Secret | Effect |
|---|---|---|---|
| `PORT` | `8000` in the Blueprint | No | Matches the Dockerfile's Gunicorn bind. |
| `APP_VERSION` | Unset on Render | No | Overrides the version reported by `/health`. |
| `RENDER_GIT_COMMIT` | Render supplies it | No | Reports the deployed commit if `APP_VERSION` is unset. |
| `DATABASE_URL` | Unset in this Blueprint | Yes | Switches from in-memory storage to PostgreSQL. |
| `SECRET_KEY` | Generated by Render | Yes | Signs session cookies. |
| `SESSION_COOKIE_SECURE` | `true` on Render | No | Restricts session cookies to HTTPS. |
| `DEMO_LECTURER_PASSWORD` | Entered during Blueprint creation | Yes | Creates the synthetic lecturer at startup. |
| `DEMO_STUDENT_PASSWORD` | Entered during Blueprint creation | Yes | Creates the synthetic student at startup. |

Gunicorn uses one worker and writes access logs to standard output. The
current startup command uses Gunicorn's default error log level.

## Verify a deployment

Replace the sample hostname with the service URL.

```powershell
$base = 'https://your-service.onrender.com'
Invoke-RestMethod "$base/health"
Invoke-RestMethod "$base/ready"
```

Expect HTTP 200 from both endpoints, status `ok` from `/health`, and status
`ready` from `/ready`. Compare the version with the commit shown in Render.
Open `/auth/login` and verify a synthetic account can sign in. Save the
health response with the public URL visible for course evidence.

## Rollback and diagnosis

On the service's **Deploys** page, select the last known good deploy and
choose **Rollback** if its build artifact is available. Otherwise, choose
**Manual Deploy → Deploy a specific commit** and provide the known good SHA.
Repeat the health and readiness checks and confirm the live version. A rollback
restarts the in-memory app. A rollback of application code also leaves any
external PostgreSQL data as it was at the time of rollback.

| Symptom | Likely cause | Action |
|---|---|---|
| Blueprint cannot find its file | Wrong branch or path | Select `main` and the root `render.yaml`. |
| Build or service startup fails | Dependency, Dockerfile, or environment error | Open the failed deploy's logs and inspect the first error. |
| First request takes a while | Free service is waking up | Wait for the service to become live, then retry `/health`. |
| Login fails after deployment | Missing or incorrect demo settings | Verify both demo passwords and the signing key in Render settings, then redeploy if changed. |
| Healthy response reports an older version | New deploy is pending or failed | Check the deploy status and compare its commit to the health response. |

For an outage, the project owner checks Render deploy logs and GitHub Actions.
If a deploy remains unhealthy after retrying, restore the last known good
version and record the failing commit and symptoms in a GitHub issue.
